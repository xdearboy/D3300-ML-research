# D3300 C 1.02 — очередь ввода и графические команды верхнего меню

Исходный B-образ `b860_102.bin` имеет SHA-256 `c7eb89f1a8e699fdd92c907989682d6d8746a46648436137cbd7e138f9afc3ff`. База ROM — `0x90020000`. Инструкции проверены в Thumb-2 с Capstone и GNU objdump. Слова таблиц прочитаны в little-endian. Младший бит сохранённых указателей на Thumb-код очищен в адресах инструкций.

## COPNOProductManager и запись очереди

- Таблица `0x916B5888` попадает в RAM по `0x1012B908` в рамках копии `0x916A73A0 → 0x1011D420` со смещением `0xE4E8`. Конструктор `0x900FDBA4` передаёт адрес таблицы и 62 записи в `0x901517B2`. Инструкция `0x901517D2` сохраняет их в полях менеджера по +0x14 и +0x18. Конструктор устанавливает vtable `0x91524B04` с RTTI `19COPNOProductManager`.
- Слот +0x60 менеджера ведёт в `0x90151CD4`. Код читает первое 16-битное поле события, вызывает слот +0x34 для преобразования, проверяет границу в `0x90151CF4..0x90151CF8` и на одном из путей выбирает объект из таблицы по индексу со stride 8 в `0x90151D36`. Когда исполняется ветвь `0x90151DCC..0x90151DDE`, соседнее слово записи подаётся в `0x902AE16A`. Функция устанавливает или сбрасывает указанные биты в поле очередь+0x10 через `ORRS` или `BICS`.
- Подобъект очереди начинается по менеджер+0x38 и инициализируется вызовом `0x901517E6`. На одном из путей менеджер копирует три слова входной записи, заменяет её второе 16-битное поле значением объект+0x12 и передаёт результат в функцию очереди `0x902AE0DA` через `0x90151E06`. У `COPNOQueueButton` отдельный путь вызова той же функции виден в `0x901AA6FA..0x901AA728`. Инициализация кнопки сохраняет адрес общей очереди в её поле +0x1C через вызов `0x90151822` и слот +0x14.
- Записывающий путь `0x902AE122..0x902AE13E` формирует 16 байт. При отдельном пороговом условии `0x902AE0FE..0x902AE10A` первое поле заменяется на `0xFFFF`. Точное назначение порога здесь не установлено.

| Смещение | Тип | Наблюдаемое значение в очереди |
|---:|---|---|
| 0 | u16 | Код события или подставленное `0xFFFF` |
| 2 | u16 | Второе поле входа. На найденном пути поступает из объект+0x12 |
| 4 | u32 | Первое слово данных |
| 8 | u32 | Второе слово данных |
| 12 | u32 | Снимок общей битовой маски из очередь+0x10 |

Метод с адресом `0x900FDBD2` из слота +0x34 вычисляет индекс объекта. Таблица `TBB` с базой `0x900FDBDE` покрывает входы от `0x3E` до `0x4E`.

| Вход | Результат |
|---|---:|
| `0x3E..0x3F` | `0x00` |
| `0x40..0x47` | `0x08` |
| `0x48..0x4A` | `0x09` |
| `0x4B..0x4D` | `0x1B` |
| `0x4E` | `0x32` |
| Другие значения | Входное значение |

Чтение из очереди проходит через `0x901515FA → 0x902ADFC2`. На пути, доходящем до `0x90151628`, менеджер снова использует слот +0x34 и записывает преобразованное значение обратно в первые два байта в `0x9015162E`. Инициализация `0x9004070C → 0x90165CBE` записывает адрес менеджера `0x1038DC54` в поле +4 объекта `COPNOHandler` по `0x103C5978`, а его адрес сохраняет в глобальной переменной `0x10128704`. Обёртка слота +0x14 `COPNOHandler` по `0x90111448` использует этот указатель на менеджер при чтении. После успешного вызова слота в `0x90323D8C` код `0x90323D96..0x90323DA0` копирует 16 байт в выходную структуру.

`CSYSCAppButtonController` получает структуру через `0x9032762A → 0x9024144C → 0x90323D7C` и читает маску в `0x90327634`. Видны обращения к индексам `0x16` и `0x17` через проверки в `0x90327648` и `0x903275DA`. В setter `0x903512A0` есть два прямых вызова: условный путь `0x903276B4` проверяет поля +2 и +4, а путь упаковки записи `0x903276EE` предварительно копирует три слова во временную структуру на стеке. Физические подписи кнопок и связь этих данных с сообщением `0x00020101` пока не установлены.

## Путь записи кнопки через CSYSCAppResumeInNormal

Инициализация `0x90321CAE..0x90321CF0` связывает две стороны передачи с одним объектом состояния внутри родительской структуры. Его смещение от начала родителя — +0x580.

- Инициализация `0x90321CD8..0x90321CDE` передаёт состояние в `0x903512C6`. Конструктор `CSYSCAppButtonController` получает этот же указатель в R1 и сохраняет его в поле +0x24 в `0x90327528`. При принятии записи `0x903276B4 → 0x903512A0` устанавливает флаг состояния по +0x10 и копирует все 16 байт по +0x30.
- В другом вызове `0x90321CCA..0x90321CD0` инициализация передаёт тот же указатель в R3 конструктору `CSYSCAppResumeCondition` (vtable `0x915360D0`). Через `0x9032825C..0x9032825E` и `0x903282DC → 0x903518C2` указатель попадает в поле +0x0C объекта `CSYSCAppResumeInNormal`, расположенного по +0x11C от начала `CSYSCAppResumeCondition`. Его vtable по `0x915327A0` установлена в `0x90332D28`. RTTI `22CSYSCAppResumeInNormal` читается через указатель `0x9153279C → 0x91505638`.
- Один из путей селектора `0x90328344` возвращает объект по +0x11C в `0x903284A8`. Инструкция `0x903284D2` вызывает слот +8, который для этого объекта указывает на `0x90332D3E`. Если состояние содержит сохранённую запись, `0x90332FAC → 0x9035128C` копирует её на стек. При выполнении проверок ветви `0x90332FB4..0x90332FC4` инструкции `0x90332FCE..0x90332FD4` передают все 16 байт в выходной буфер. Отдельное поле результата получает байт `3` или `0x12` в зависимости от поля состояния +0x2C. Оба значения записываются отдельно от самой записи кнопки.

После возврата `0x903284DC..0x903284E6` переносит байт результата и запись в выходные параметры. `0x903284F2` выбирает ветку по этому байту в `0x90328522..0x9032852C`. Для `3` ветка вызывает `0x90241522 → 0x90323A08 → 0x903307DC`, для `0x12` — `0x90241526 → 0x90323A28 → 0x90330BA4`. Обе ветки передают первые 16 бит исходной записи как идентификатор, если его младший байт ненулевой, и `−1` в противном случае.

## Условный переход от записи кнопки к активации меню

Для служебного кода `0x12` и нормализованного идентификатора `0x0B` прослежен путь, если ранние проверки в `0x90330BB6..0x90330BF8` не обработали запрос. Сравнение по `0x90330C02` ведёт в `0x90330C84`, где идентификатор передаётся в `0x90252D9E`. Байт 11 таблицы `0x90252DAA` ведёт в `0x90252E40`, которое выбирает `0x1B` для следующей проверки. Функция `0x902520F6` для этого значения возвращает 0 или 2 через `0x90252140..0x9025214A`. Обе ветви `0x90330C66..0x90330C7E` формируют запрос через `0x9033042A` или `0x90330452` соответственно. Вторая функция создаёт другой тип параметров, `CSTBLActivateParam` (vtable `0x91523720`), поэтому к меню через рассматриваемый путь приводит результат 0. В первой ветви `0x90330442` передаёт параметр активации 1.

В ветви служебного кода `3` адрес `0x9033094A` также вызывает `0x9033042A`, с параметром активации 6. Этот путь требует результата 3 от `0x902520F6` в `0x90330906` и прохождения более ранних проверок. Статический путь от результата 3 доказан, конкретное рабочее состояние для него остаётся открытым.

На успешном пути `0x9033042A` создаёт объект через `0x90100770 → 0x90100760`. Конструктор ставит vtable `0x91521C94`, RTTI `18CMENUActivateParam`. Функция `0x9033043A..0x9033044A` записывает байт типа 0, нулевой второй байт и указатель на параметр по +4. Возвращённый результат `0x903284F2` сохраняет как запрос с собственным служебным кодом 1 через `0x90328594 → 0x9032D512`. Сама пара слов запроса попадает в состояние по +0x20. При обработке отложенного запроса `0x9032D564` читает их на ветви 1 и передаёт в `0x9032D4AC`. Через `0x90241502 → 0x90324956 → 0x9032492C` байт типа 0 выбирает идентификатор приложения `0x40000003`. Исходная пара в ROM находится по `0x9145FA24`.

При переходе в другое приложение `0x9032481E` передаёт менеджеру адрес назначения и указатель на параметр. Инициализация `0x90022D76..0x90022DB8` передаёт объект менеджера в конструктор `CUIFMJAppManagerHandle` `0x90024B48`. Тот сохраняет его по +0x34 и связывает задачу с портом handle+0x14 через `0x9011BC04`. На стороне отправителя слот +0xC вторичного интерфейса `0x91532900` ведёт через `0x90024CDC` в `0x90024C36`. Там формируется сообщение `0x00020301` и отправляется через `0x90031938` в `0x90024CC2`. У получателя vtable `CUIFMJAppManager` по `0x9151F05C` направляет слот +0x10 в `0x90024AD8`. Диспетчер `0x9002D2B2` выбирает первую пару RAM-таблицы `0x10125418`, то есть слот 0 вторичного интерфейса `0x9151F0CC`. Его метод `0x90024070` при результате 0 от `0x90023FAE` копирует идентификатор назначения и объект параметров в поля менеджера +0xDC и +0xE0.

На пути, где экземпляр назначения нужно создать, `0x90023BD6` переходит к `0x90023A62`. Вызов `0x90023A9C` передаёт менеджером сохранённый идентификатор `0x40000003` в слот 0 объекта из поля +0x14. Инициализация `0x9002153A..0x90021558 → 0x90024C08` записывает туда `CJAPIJApplicationCreator`. Его vtable `0x91536474` ведёт в `0x900230BE`. Ветка `0x40000003` возвращает вторичный интерфейс `CUIFAJAppHandle+0x2C` через `0x9002337C`. Менеджер сохраняет интерфейс в записи списка и извлекает его через `0x90023826` в `0x90023AD8`. В `0x90023AEE` он передаёт объект параметров из +0xE0 в слот +4 этого интерфейса. Запись `0x9151D358` указывает на `0x9002D594`, который корректирует this и переходит в `0x9002D546`, отправитель запроса `0x00020101` к `CMENUController`.

Таким образом, нормализованный `0x0B` в ветви `0x12` может привести к программной активации меню при указанных условиях. Происхождение `0x0B` от конкретной физической кнопки и код подтверждения внутри меню пока открыты.

## Чтение кнопок при открытом меню

У `CMENUController` есть собственный путь чтения очереди через слот +0x64. Запись `0x9151B690` указывает на `0x90032CA4`. При аргументе `0x40` метод вызывает `0x90032B86` из `0x90032CC0`. Тот получает `COPNOHandler` через `0x90165CB2` и вызывает его слот +0x14 в `0x90032BA2`, то есть тот же метод чтения, которым пользуется системный контроллер кнопок. После успеха он отдельно проверяет `0xFFFF`. Для остальных принятых записей первый halfword идёт через `0x90032BEC..0x90032BF2` в `0x90252D9E`, а последнее слово отдельно передаётся через `0x90251A40`.

На пути, где `0x90252D9E` возвращает 0, `0x90032C18` создаёт объект `CJAPFButtonEventParam` через `0x9012B82A → 0x9012B810`. Его vtable `0x9152BD0C` связывается с RTTI `21CJAPFButtonEventParam` по `0x91504930`. Код `0x90032C20..0x90032C3A` пропускает слова данных 0 и 1 из записи в поле параметра +0x0C через `0x9012B85C`. Затем `0x90032C7C → 0x90032AFA` передаёт переведённый идентификатор и объект в слот +0x10 активного экрана. Метод `0x90031D2A → 0x9003FF50` получает указатель на этот экран из первой записи списка контроллера. Сброс очереди при `0xFFFF` проходит через отдельную ветку `0x90032BCC → 0x90032B70`.

Для активного экрана `CMENUTopMenuView` слот +0x10 указывает на `0x9025A85E`. Для входа `0x0B` преобразование даёт `0x1B`, и соответствующий байт таблицы `0x9025A86E` выбирает ветку `0x9025A8D2`. Она вызывает слот экрана +0x40, то есть `0x9025AD54` для этого класса. Функция читает сохранённое поле +0x0C и с учётом состояния экрана выбирает дальнейший слот. Например, при нулевом поле и нулевом значении локального состояния `0x9025ADDC` выбирает +0x48, то есть `0x90254F36`. Там значение `0x1B` направляется через `0x90255042` в слот +0x1E4, который у верхнего экрана указывает на `0x90255B6C` с инструкцией `BX LR`. Это один из путей для данной комбинации состояния и данных. Смысл других действий зависит от выбранного экрана и его состояния.

В таблице объектов ввода слот `0x0B` содержит пару `0x103E3C8C, 0x00000100` по RAM-адресу `0x1012B960`. Инструкции `0x900FDE18..0x900FDE1E` передают тот же адрес объекта и ID `0x0B` конструктору `COPNOQueueButton`. Это связывает индекс с объектом очереди и битом состояния. Физический источник события пока открыт.

## Логическое подтверждение пункта верхнего меню

Для записи с нормализованным идентификатором `0x0C` и первым словом данных 1 контроллер идёт по следующему пути при активном верхнем экране и допустимом состоянии экрана.

| Участок | Проверенный переход |
|---|---|
| Преобразование идентификатора | `TBB` по `0x90252DA6` с базой `0x90252DAA` выбирает `0x90252DE6`. Этот путь записывает код `1` в выходное слово и возвращает 0. |
| Передача события | `0x90032C36..0x90032C3A` сохраняет значение 1 в поле +0x0C объекта `CJAPFButtonEventParam`. Слот +0x10 верхнего экрана ведёт в `0x9025A85E`, а индекс 1 его таблицы `0x9025A86E` выбирает `0x9025A8D2` и слот экрана +0x40. |
| Выбор обработчика | При значении локального состояния 0 или 1 метод `0x9025AD54` с ненулевым полем параметра +0x0C вызывает слот +0x54, затем слот +0x44. Для `CMENUTopMenuView` слот +0x44 ведёт в `0x90254DD4`. На пути, дошедшем до `TBB` `0x90254E18`, индекс 1 выбирает `0x90254E7E`. Эта ветка берёт слот +0x12C из `0x9151D9A0` и вызывает `0x90076FF4` с объектом события. |
| Действие по текущему пункту | `0x90076FF4` получает идентификатор текущего графического пункта виртуальным вызовом `0x90077030`. После маски `0x07FFFFFF` индексирует таблицу записей длиной 24 байта по `0x9144EEFC`. Для примера `0x0800005A` строка начинается по `0x9144F76C`, а поле +0x0C равно `0x0F`. Для этого пункта `TBB` `0x90077082` ведёт в `0x90077190`, где поле из таблицы и аргумент 1 передаются в `0x9025B068`. |
| Запрос экрана | `0x9025B068` получает объект параметров. На успешном пути `0x9025B094` сохраняет в его данных идентификатор экрана `0x0F`. В `0x9025B0A2` функция передаёт параметры с кодом операции 3 в виртуальный интерфейс из поля экрана +4. |

Таким образом, на указанном пути логическое событие `0x0C → 1` запускает действие для текущего пункта меню. Для примера `0x0800005A` это выдача запроса на экран `0x0F`. Слот `0x0C` со стороны ввода соответствует `COPNOQueueButton` по `0x103E3CAC` и маске `0x00000200` (пара по `0x1012B968`, вызов конструктора `0x900FDE30`). Физическая привязка к надписи OK остаётся открытой. Идентификатор `0x0F` в примере относится к целевому экрану.

## Фильтр COPNOQueueButton для 0x0B и 0x0C

Метод слота +0x2C `COPNOQueueButton` по `0x9013DDCC` сначала вычитает 4 из первого halfword записи и принимает только диапазон `0x04..0x15`. Его `TBB` по `0x9013DDE4` делит диапазон на три проверенные группы.

| Входной ID | Ветка | Условие до копирования полей +4 и +8 |
|---|---|---|
| `0x04..0x05` | `0x9013DDFA` | первое слово данных по +4 равно 1 |
| `0x06..0x0B` | `0x9013DE14` | дополнительных проверок нет |
| `0x0C..0x15` | `0x9013DE00` | слово по +4 равно 1, `0x9016E0A4` возвращает 0 и `0x9016E076` возвращает код успеха |

После прохождения соответствующей ветки `0x9013DE14..0x9013DE18` копирует два слова данных из входной записи в объект. Поэтому для `0x0B` сам фильтр класса не требует `value_1 == 1`, а для `0x0C` единица необходима, но недостаточна без двух проверок текущего состояния. Это согласуется с уже прослеженным логическим подтверждением пункта меню, где поле `value_1` равно 1.

Этот фильтр не устанавливает физические подписи клавиш. В методе `0x90151CD4` ID выбирает объект таблицы, слот +0x28 выполняет предварительную проверку, а слот +0x2C вызывает описанный фильтр. Статический код, который формирует записи `0x0B/0x0C` из GPIO или иного аппаратного транспорта, пока не установлен.

Офлайн-инструмент `tools/d3300_opno.py` теперь выводит поле `queue_button_filter`. Значение `accepted: null` означает, что формат записи подходит, но результат двух runtime-проверок нельзя вывести из дампа самой записи.

## Отдельный агрегатор COPNOButton по индексу 0x1B

Инициализация `0x900FDF34..0x900FDF3A` создаёт объект по `0x103E3E8C` с идентификатором `0x1B` вызовом конструктора `0x9013CDD0`. Конструктор ставит vtable `0x91516630`; RTTI этого класса указывает на строку `11COPNOButton`. Пара менеджера для индекса `0x1B` лежит по `0x1012B9E0` и содержит тот же объект, но нулевую маску состояния.

Метод `0x9013CF56` этого класса разбирает диапазон `0x40..0x4D`. Для `0x48..0x4A` он вызывает `0x9013CE5C`, которая ставит или очищает биты 0, 1 и 2 в поле объекта +8 и сохраняет отдельные значения по +0x1C, +0x20 и +0x24. Аналогичная функция `0x9013CDFE` обрабатывает `0x4B..0x4D`. Общий нормализатор менеджера `0x900FDBD2` сводит первую тройку к индексу `0x09`, вторую — к `0x1B`.

Этот специализированный агрегатор отличается по классу и обработчикам от `COPNOQueueButton` по индексам `0x0B` и `0x0C`. Следовательно, наличие агрегированных входов `0x48..0x4D` не подтверждает физическую привязку MENU или OK к `0x0B/0x0C`; эти тракты нельзя объединять без найденного производителя исходных записей.

## Регистрация IOPNOOperationReceiveObserver

Конструктор менеджера `0x900FDBA4 → 0x901517B2` получает массив из восьми указателей по `0x9144C24C`. При запуске метод `0x90151188` перебирает этот массив из полей менеджера +0x1C/+0x20. Для каждого объекта он передаёт `manager+0x10` в `0x901AA586`. Эта функция сохраняет указатель в глобальной переменной `0x101410D4`, затем вызывает слот +0x0C объекта.

Шлюз `0x901AA5C0` загружает указатель из `0x101410D4` и вызывает его первый виртуальный слот с указателем на 12-байтную запись. Вторичная vtable менеджера начинается по `0x91524B78`; её первый слот указывает на thunk `0x90151EB6`, который вычитает `0x10` из `this` и переходит в `0x90151CD4`. Поэтому доказанная цепь локального производителя выглядит так:

`COPNOOperationBase producer → 0x901AA5C0 → manager+0x10 → 0x90151EB6 → 0x90151CD4`.

Восемь указателей операций находятся в RAM по `0x1012B8E8..0x1012B904`. Их конструкторы вызываются в `0x900FDCD4..0x900FDD52`; ROM-массив адресов этих RAM-слотов расположен по `0x9144C24C`.

Статический поиск прямых переходов к `0x901AA5C0` в проверенном B-образе находит 19 мест. Проверенные локальные производители формируют события `0x1C..0x27`, `0x2C..0x33`, `0x38`, `0x3B`, `0x3C` и `0x3D`; часть значений выбирается таблицами по входным параметрам. Ни один прямой вызов не формирует `0x0B` или `0x0C`. Это не доказывает отсутствия косвенного либо межзадачного производителя, но исключает восемь зарегистрированных локальных операций как прямой источник рассматриваемых двух ID.

Следующая подтверждаемая граница — диспетчер задачи менеджера `0x90151C6E`, принимающий сообщения семейства `0x20062C10..0x20062C1A`. Он вызывает отдельные обработчики, которые передают данные объектам таблицы. Ниже разобран отдельный источник сообщения `0x20062C13`; проверка показала, что он не производит нужные ID `0x0B/0x0C`.

## Отдельный путь состояний CSYSCDeviceManager

RTTI по `0x91503450` связывает первичную vtable `0x91523814` с классом `18CSYSCDeviceManager`. Его общий диспетчер `0x9031FCA2` использует 52-элементную таблицу по `0x9144B5E8`. Вход `0x2B` выбирает callback `0x90320168`, который переходит в `0x903200E0` и опрашивает девять дескрипторов состояний по `0x9144B858`.

Каждый дескриптор имеет stride 28. `0x903200BC` передаёт его первый ID в запрос `0x90241450`, сравнивает результат со значениями по +4 и +0x10 и выбирает callback по +8 либо +0x14. Поэтому записи по `0x9144B8AC` и `0x9144B8C8` не являются входными событиями: это опросы селекторов состояния `0x33` и `0x35`. Оба используют callback `0x9032037E` для результата 1 и `0x90320392` для результата 0.

Callbacks ведут в `0x90322E90` и `0x90322E12`. Для локальных observer-объектов они вызывают преобразователь `0x90320072`; его `TBB` по `0x9032007A` задаёт следующую таблицу.

| Исходный ID | `0x2C` | `0x2D` | `0x2E` | `0x2F` | `0x30` | `0x31` | `0x32` | `0x33` | `0x34` | `0x35` | `0x36` | `0x37` | `0x38` |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| ID объекта | `0x02` | `0x03` | `0x04` | `0x0A` | `0x09` | `0x05` | `0x06` | `0x0B` | `0x07` | `0x0C` | `0x08` | `0x00` | `0x01` |

Критическое разделение видно непосредственно в `0x90322E12/0x90322E90`: нормализованный результат сохраняется в R5 и передаётся только локальным рассылкам `0x9031FDCA` и `0x9031FE28`. В межзадачный венер `0x90241454` через R0 передаётся исходный селектор из R6, то есть `0x33` либо `0x35`. Венер ведёт в `0x90323E24`, который выбирает слот +0x2C/+0x30 `COPNOHandler`; прокси `0x9011148C/0x90111492` вызывают `0x90151518/0x90151582` и создают сообщение `0x20062C13` с исходным ID и состоянием 1/0.

Обработчик сообщения `0x90151AE8` снова вызывает штатный слот +0x34 нормализации менеджера. Проверенный нормализатор `0x900FDBD2` преобразует только диапазон `0x3E..0x4E`; `0x33` и `0x35` остаются неизменными. Следовательно, этот task-путь выбирает объекты `0x33/0x35`, а не `COPNOQueueButton` `0x0B/0x0C`. Совпадение локального отображения `0x33 → 0x0B` и `0x35 → 0x0C` нельзя использовать как доказательство физической привязки MENU/OK. Это проверенный отрицательный результат; поиск производителя настоящих записей `0x0B/0x0C` продолжается отдельно.

## Аудит прямых потребителей COPNOHandler

Постоянный статический индекс для проверенного образа находит 73 прямых Thumb `BL` к getter `0x90165CB2`. У каждого места проверена загрузка виртуального слота после возврата getter. Единственное прямое место, выбирающее отправляющие слоты +0x2C/+0x30, — `0x90323E24` с вызовом getter по `0x90323E34`. Остальные прямые потребители используют читающие и управляющие слоты, включая +0x10, +0x14, +0x20, +0x24, +0x28, +0x34, +0x38, +0x40, +0x44, +0x50 и +0x58.

Все прямые переходы к венеру `0x90241454 → 0x90323E24` также перечислены индексом. Два динамических места — `0x90322E30` и `0x90322EB8`; как показано выше, они передают селекторы `0x33/0x35`. Остальные проверенные места используют явные ID `0x2D`, `0x2E`, `0x31`, `0x32` или `0x4E`. Прямого ROM-вызова этого шлюза с `0x0B` либо `0x0C` нет.

Два helper-а подтверждают отдельное направление «ID интерфейса → чтение состояния», а не производство события. `0x90257F1C` преобразует аргумент `0x0B` в selector `0x16`, `0x0C` в `0x17` и вызывает читающий слот +0x10 `COPNOHandler`; его два прямых вызывающих места передают только `0x1A`. Аналогично `0x90250EE2` преобразует `0x0C` в `0x17` перед тем же слотом +0x10. Эти сравнения не создают входные записи менеджера.

Getter сохраняется как alias: `0x900FD4E2` получает указатель от `0x90165CB2`, а затем в `0x900FD4F0` передаёт его в `0x9013B9AA`. Дизассемблирование setter-а показывает запись R1 по `0x1049157C` (база `0x10491468` + `0xB4` + `0x60`). Индекс находит один прямой вызов setter-а — `0x900FD4F0`. Дополнительный полный read-only индекс образа (`599744` xrefs, SHA-256 проверен) не находит ни одного выровненного ROM-pointer/branch reference, нацеленного непосредственно на `0x1049157C`; это сужает поиск, но не исключает вычисляемые адреса, RAM-код или runtime transport. Это подтверждает сохранение alias, но само по себе не показывает его последующих читателей.

Ранее найденные `0x901A4900/0x901A4904` — другой путь, и использовать их как читателей alias было ошибкой. В `0x9013BB06` ветвь ключа `0x0B` вызывает setter `0x901A4900`; там R1 записывается в объект+`0x50`. Проверенные вызывающие места передают в R2 значения 0/1, а парный `0x901A4904` проверяет это поле и связанное состояние. В данном пути объект — `0x1049151C`, поэтому поле находится по `0x1049156C`, отдельно от alias по `0x1049157C`. Межпроцедурный поиск читателей сохранённого alias ещё не завершён.

## Кандидатный маршрут через CKRCCCommandManager

В этой же области прошивки найден общий двухтабличный диспетчер. RTTI `0x91503790` указывает на имя `19CKRCCCommandManager` (`0x9150C56A`); его vtable начинается методами `0x9013B6BC`, `0x9013B76E`, `0x9013B786` по адресу `0x915241F8`. Последние два метода читают таблицы `0x91478498` и `0x91478640`; первая содержит 106 индексных элементов, вторая расположена на `+0x1A8`. Это подтверждается кодом, а не только эвристикой индекса.

Диспетчер `0x900FAB14` классифицирует индекс через TBB по `0x9013B7B0` (внутри функции `0x9013B7AA`), выбирает одну из таблиц и вызывает у найденного объекта виртуальный слот `+0x14`. По байтам TBB индекс `0x0B` выбирает первую таблицу, а `0x0C` — вторую. Записи для этих индексов: первая таблица `[11]` → `0x1049151C`, вторая `[12]` → `0x10491580`. Последний адрес находится сразу после сохранённого alias `0x1049157C`.

Детальный аудит опроверг гипотезу о том, что `0x10491580` может быть объектом кнопки:
- `0x9013BC60` — единственный прямой вызов конструктора `0x9019A340` с `R0 = 0x10491580`.
- Конструктор `0x9019A340` устанавливает vtable `0x9151F6F0`.
- Запись RTTI `0x91502950` указывает на строку `17CKRRCCameraStatus` по `0x9150AFBB`.
- Слот `+0x14` vtable — это `0x90350DD0`. Он читает поле объекта `+0x84` и возвращает слово со смещением `+0x0C` этой структуры.
- `0x900FAB14` вызывает этот слот и передаёт возвращённый указатель ARM-процедуре `0x90274BBC` (реализация `memcpy`).
- Следовательно, индекс `0x0C` диспетчера CKRCC — это тракт чтения статуса камеры (`CKRRCCameraStatus`), а не генератор событий физических кнопок.
- Сохранённый alias `COPNOHandler` по `0x1049157C` — это соседняя отдельная глобальная переменная. Конструктор `0x9019A340` не обращается к `object-4`, поэтому пространственное соседство не означает связности.

Для сравнения, реальный тип `COPNOQueueButton` имеет RTTI по `0x915023DC`, vtable по `0x9151DE6C` и конструктор `0x9013DD94`. Его слот `+0x14` ведёт в `0x901AA6DA`, где R1 сохраняется в поле объекта `+0x1C`. Индекс находит 36 прямых вызовов конструктора только в диапазоне `0x900FDD6C..0x900FE06A`; дизассемблирование показывает смещения от баз `0x103E3B14`, `0x103E3C1C` и `0x103E3D2C`. Эти экземпляры не совпадают с `0x10491580`.

Автоматический полный просмотр: `python3 tools/d3300_dispatch.py b860_102.bin --tbb 0x9013B7B0 --count 106 --all --array 0x91478498 --array 0x91478640`. Он проверил 106 индексов и нашёл ненулевые записи в 69; адреса целей затем сверялись с дизассемблированием.

Практический итог: среди статически разрешённых прямых путей B-образа источник `0x0B/0x0C` не найден. Кандидатный маршрут через CKRCC `0x0C` закрыт как чтение статуса камеры. Оставшийся поиск сужен до непрямых вызовов через сохранённые aliases, runtime-кода в RAM и внешнего транспорта.

## Проверенный читающий шов состояния кнопок: 0x9035128C

В паре к пишущему шлюзу `0x903512A0` подтверждён контракт вспомогательной процедуры `0x9035128C`:
- Вход: `R0` — указатель на объект состояния кнопки, `R1` — `NULL` (для опроса готовности) либо указатель на 16-байтный буфер приёмника.
- Логика: процедура читает флаг готовности `[R0, #0x10]`. Если флаг не равен нулю и `R1 != NULL`, 4 слова (16 байт) копируются из `[R0, #0x30]` по адресу `R1` через `LDM/STM`. В конце возвращается значение флага готовности `[R0, #0x10]` в `R0`.
- Наблюдение: это подтверждённый read-side seam для безопасного пассивного чтения последней принятой записи без модификации структуры.

## Источник запроса 0x00020101 к контроллеру меню

Для ветви с входом `0x40000003` в таблицу `0x900230F0` код инициализации использует `CMENUController` по `0x10317C90`. Конструктор `0x9002A280`, вызванный из `0x90023186`, ставит vtable `0x9151B62C`. В `0x900231B8..0x900231C2` адрес того же контроллера передаётся конструктору `CUIFAJAppHandle` по `0x10317D10`. Его vtable `0x9151D304` связана с RTTI `15CUIFAJAppHandle` по `0x91502104`. Цепочка `0x9002D466 → 0x9011BC04` соединяет порт handle+0x14 с контроллером. Инструкция `0x9011BC1E` сохраняет адрес вторичного интерфейса handle+0x18 в контроллер+0x0C. Слот цикла `0x9015B270` читает из этого поля. Конструктор handle сохраняет указатель на первичный интерфейс в собственном поле +0x34 по `0x9002D480`.

Слот +0x18 первичной vtable `CUIFAJAppHandle` по `0x9151D31C` ведёт в `0x9002D546`. Метод строит сообщение через `0x9002D568..0x9002D574` с константой `0x00020101` из `0x9002D7DC` и объектом с RTTI `24CUIFFActivateSessionData` (vtable `0x91538EB4`), затем вызывает `0x90031938` с портом из handle+0x34. На успешном пути функция выделяет запись, копирует код в её первое слово через `0x90034EC0` и отправляет запись вызовом слота порта +4 в `0x90031968`. Для экземпляра, соединённого с `CMENUController`, запись из этого порта попадает в `0x90031E30 → 0x9003FD72`, где `0x00020101` выбирает `0x900F466C`. Это штатный путь отправки запроса из UI. Привязка вызывающей стороны к физической кнопке остаётся открытой.

## Путь CMENUTopMenuView к CGUICTask

RTTI `16CMENUTopMenuView` связывает vtable `0x9151D874` с экраном верхнего меню. Конструктор устанавливает этот адрес в `0x900760FE`. Метод в слоте `0x9151D888` вызывает `0x90255E56` через `0x900766C8`. Общая функция настройки получает `CGUICEntry` по `0x10342B88` через `0x900E8BA4`, вызывает его слот +0x1C с R1=0 и сохраняет результат в экран+0x28 в `0x90255FB0`. Слот соответствует `0x9003EE14`. При статусе 0 или 2 он использует подобъект `CGUICEntry+0x58`, конструктор которого устанавливает vtable `CGUICView` по `0x9154ADC8`.

Код `0x9007676A..0x900767EE` формирует 0x60-байтный дескриптор с первыми двумя словами `0x4C` и 1. Он вызывает `0x90256208` с дескриптором и отдельной структурой параметров. Первое слово параметров выбирает слот +0x38, если оно равно 1, и слот +0x34 иначе. Оба пути формируют 0x74 байта параметров, подготавливают сообщение и передают его в слот +4 порта при успешном выделении записи.

| Слот CGUICView | Метод | Код в первом слове | Вызов отправки |
|---|---|---|---|
| +0x34 | `0x900EEAE6` | `0x00063402` | `0x900EEBE0` |
| +0x38 | `0x900EEC40` | `0x00063416` | `0x900EED92` |

Оба метода используют поле `CGUICView+0x18`. Инициализация `0x9003E8CA..0x9003E8EC → 0x900EEA6E → 0x9012F9CA` сохраняет туда адрес `CGUICEntry+0x38`. В `0x9003E820..0x9003E834` вызывается настройка этого же порта через `0x9011BC48` и `0x9011BC6A`. Конструкторы `0x9003E70A → 0x9011BBF0 → 0x9027457C` ставят vtable порта `0x91524164`, RTTI `19CJAFFMessageComPort`. Слот +4 указывает на `0x9027469C`, который передаёт запись в системный вызов через `0x90225E2C`, используя идентификатор из поля порт+8.

`CGUICTask` находится по `CGUICEntry+0x0C` и получает адрес вторичного интерфейса того же порта, `CGUICEntry+0x3C`. Это записывает `0x9011BC62` в поле задача+0x0C при вызове `0x9003E82A`. Вторичная vtable `0x9152418C` ведёт через +4 в `0x902746FA → 0x902746BC`. После коррекции указателя на −4 эта функция использует тот же идентификатор порта для чтения через `0x90225E24`. Цикл `0x9015B250` вызывает этот интерфейс в `0x9015B270`, затем при результате `0xF0000000` передаёт управляющей функции задачи полученную запись. Конструктор `0x900EE2D0` устанавливает vtable задачи `0x9154AD48`, где +0x10 указывает на `0x900EE2FC` (RTTI `9CGUICTask`).

Получатель читает код из первого слова. Команда `0x00063402` выбирает индекс 2 таблицы `TBB` с базой `0x900EE326`. Байт `0xB3` ведёт в `0x900EE48C`. Команда `0x00063416` выбирает индекс 3 таблицы с базой `0x900EE348`. Байт `0xAE` ведёт в `0x900EE4A4`. Обе ветви извлекают из сообщения данные и объект `CGUICView+4`, который отправитель записал в поле сообщения +0x10. Вторичная vtable этого объекта `0x9154AE7C` даёт следующие переходы.

| Команда | Вызов в CGUICTask | Метод CGUICView после коррекции this |
|---|---|---|
| `0x00063402` | `0x900EE4BA`, слот +0x10 | `0x900EFA4A → 0x900EF88E` |
| `0x00063416` | `0x900EE4BA`, слот +0x14 | `0x900EFCA0 → 0x900EFA4E` |

При нулевом поле view+0x610 обе реализации передают параметры менеджеру из view+0x604 в `0x9012A73C`. Сделано это в `0x900EF8D4` и `0x900EFAFC`. Инициализация `0x9003E8F0..0x9003E8F8 → 0x900EEA68` использует для этого поля объект по `0x10383580` из `0x90129768`. Его конструктор `0x9012AD9E → 0x9012AD16` устанавливает vtable `0x9154AD28` с RTTI `9CGUICDraw`. Код `0x9012A73C` копирует поля в структуру и вызывает `0x90129EFE`.

У `0x90129EFE` есть ветвь для ранее выбранного объекта вывода, если адрес этого объекта ненулевой и поле записи +0x80 равно нулю. В `0x90129FA6` она получает поля через слот объекта +0x5C, затем вызывает `0x90129AA6`. Та проверяет ненулевое поле +0x9C и две границы по halfword перед вызовом `0x901297F2` в `0x90129B06`. Эта функция берёт два размера и указатель из аргументов, передаёт размер строки `((a+7)&~7)*4` и выполняет серию вызовов через венеры. Например, вызов `0x9012986A` передаёт `0xC1`, размеры и размер строки через `0x90225D70 → 0x1009DAC8`. Возвращённое значение передаётся в `0x90129894` через `0x90225D88 → 0x1009C64C`. Оба адреса реализации лежат за пределами подтверждённых копий ROM→RAM, поэтому имена этих операций и назначение указателя остаются открытыми.

Отдельно RTTI `23CDPCNGPUDrawAreaManager` связан с vtable `0x91532AD4`. Её слот +0xC ведёт через `0x900F8FC6 → 0x9015457A` к вызовам `DrawBufferCreate` и `DrawBufferSelect` в `0x901545D4` и `0x901545DE`. Связь этих операций с конкретной командой верхнего меню и путь до записи пикселей пока открыты.
