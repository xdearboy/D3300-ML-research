# D3300 C 1.02 — сопоставление объектов кнопок и графических буферов

Образ B имеет SHA-256 `c7eb89f1a8e699fdd92c907989682d6d8746a46648436137cbd7e138f9afc3ff`. Адреса относятся к базе `0x90020000`. Код ниже проверен в Thumb-2. Таблицы прочитаны как little-endian слова.

## Таблица объектов ввода

По `0x916B5888` находятся последовательные пары адресов объектов и 32-битных значений. Их первые адреса совпадают с адресами, передаваемыми конструкторам в `0x900FDD56..`:

| ID конструктора | RAM-адрес объекта | Слово в паре |
|---:|---|---|
| 0 | `0x103E3B14` | `0x00000000` |
| 1 | `0x103E3B3C` | `0x00000001` |
| 2 | `0x103E3B5C` | `0x00000002` |
| 3 | `0x103E3B7C` | `0x00000004` |
| 4 | `0x103E3B9C` | `0x00000008` |
| 5 | `0x103E3BBC` | `0x00000010` |
| 6 | `0x103E3BDC` | `0x00000020` |
| 7 | `0x103E3BFC` | `0x00000040` |
| 8 | `0x103E3C1C` | `0x00000000` |
| 9 | `0x103E3C44` | `0x00000000` |
| 10 | `0x103E3C6C` | `0x00000080` |

ID 1..7 и 10 передаются конструктору `0x9013DD94`, ID 0 передаётся `0x9013DA58`, а 8 и 9 — `0x9013CDD0`. Это сопоставление следует из инструкций загрузки адреса и R1 перед вызовом, а также из сохранения R1 по смещению объекта +0x10 в `0x902ADF94`. Степени двойки являются кандидатами в битовые маски, их потребитель и связь с физическими подписями пока не установлены. Таблица расположена в ROM вне четырёх ранее перечисленных источников RAM; её использование во время выполнения ещё требует отдельного подтверждения.

## Код штатного меню

RTTI по `0x91501D8C` ссылается на строку `15CMENUController` по `0x9150A101`. Связанная vtable начинается с указателя на RTTI по `0x9151B628`. В её слоте `0x9151B664` находится Thumb-указатель `0x9002A401`.

Метод `0x9002A400` при ненулевом R1 читает байт `[R1,#0xC]` и затем вызывает указатель из объекта R1 через `BLX R1` в `0x9002A41A`. Далее `0x9002A44E` сравнивает прочитанное значение с 9, а `0x9002A45C` использует его как индекс `TBB`. Это подтверждает диспетчеризацию по полю входного объекта в методе класса меню. Физическое происхождение поля и связь его значений с MENU/OK не установлены. Адреса переходов таблицы не следует дизассемблировать как Thumb-инструкции.

Другой слот этой vtable по `0x9151B63C` содержит `0x90031E31`. Метод `0x90031E30` загружает поле объекта +0x28 и вызывает `0x9003FD72` с входным R1. В `0x9003FD72` строится локальная структура через `0x900F00E2`, её поля извлекаются вызовами `0x9003FD1A` и `0x9003FD0A`, затем результат сравнивается с `0x20000001`. При совпадении слово `[SP,#8]` попадает в проверку диапазона и таблицу переходов `0x9003FDAC`. Это наблюдаемый путь обработки сообщения от виртуального метода контроллера к набору обработчиков. Происхождение входного R1 и смысл числовых кодов ещё не установлены.

Путь удалось продолжить в обе стороны. Цикл `0x9015B250` получает указатель в `[SP]` через косвенный вызов `0x9015B270`. При результате `0xF0000000` инструкция `0x9015B280` вызывает слот vtable +0x10 с этим указателем в R1. Для `CMENUController` это `0x90031E30`. `0x900F00E2` копирует первое слово входной записи в локальное поле, которое вызывающий `0x9003FD72` читает как `[SP,#8]`.

Для первого слова записи `0x00020101` сравнение составного кода с `0x20000001` проходит, а прибавление `0xFFFDFEFF` даёт индекс 0. Первый байт таблицы `0x9003FDB0` равен 6 и направляет исполнение в `0x9003FDBC`, где вызывается `0x900F466C`. Код `0x900F468E..0x900F4696` загружает объект и вызывает его vtable +0x38. Если это тот же объект `CMENUController`, слот `0x9151B664` указывает на `0x9002A401`, и управление достигает описанного выше метода `0x9002A400`. Идентичность объектов на всём косвенном пути остаётся условием, которое необходимо доказать отдельно. Назначение сообщения `0x00020101` и соответствие физической кнопке также неизвестны.

## Операции с графическим буфером

Рядом с кодом есть строки диагностики `DrawBufferCreate` по `0x9147FB28`, `DrawBufferSelect` по `0x9147FB48`, `DrawBufferDestroy` по `0x9147FB59`, `DrawBufferSwap` по `0x9147FB6B` и `DrawBufferQuery` по `0x9147FB7A`. Следующие связи подтверждаются кодом и диагностическими аргументами, но точные сигнатуры API пока не восстановлены.

| Функция | Наблюдаемое поведение | Подтверждённый вызов |
|---|---|---|
| `0x9029E720` | поиск свободной записи среди 20 записей с шагом 20 байт по `0x104A0868`; создание с последующим заполнением записи | `0x901545D4`, также `0x90154732` |
| `0x9029E848` | проверка индекса, загрузка двух полей записи и вызов венера `0x90225C40`; диагностика использует `DrawBufferSelect` | `0x901547A0` |
| `0x9029E8B0` | проверка индекса, освобождение связанных ресурсов и обнуление признака записи; диагностика использует `DrawBufferDestroy` | `0x90154598` |
| `0x9029E940` | проверка индекса и вызовы венеров; диагностика использует `DrawBufferSwap` | `0x90154642` |
| `0x9029E9B2` | проверка индекса и селектора меньше 6, вызов венера с параметром из таблицы; диагностика использует `DrawBufferQuery` | `0x901547B2` |

В `0x901545CE..0x901545D4` два halfword из входной структуры поступают в R0/R1 функции создания. В `0x90154732` другой вызывающий код также передаёт ей два halfword. Их смысл как ширины и высоты правдоподобен, но без полного контракта остаётся гипотезой.

Функция `0x90169286` копирует 0x30 байт из `0x9145D368` в стек и передаёт шесть пар 32-битных значений в `0x9029EA3C`. Пары равны `(1920,1080)`, `(1920,1080)`, `(720,480)`, `(720,480)`, `(960,540)`, `(960,540)`. На пути `0x9029EA80..0x9029EA96` для каждой пары вычисляется `((a+7)/8)*b*32` для неотрицательных значений. Эти числа согласуются с размерами изображений, однако по одним константам нельзя установить формат пикселей, назначение каждого буфера или адрес кадра.

## Границы результата

Связь методов управления буферами с конкретной реализацией штатного меню остаётся неразрешённой. Не подтверждены коды физических MENU/OK, формат пикселей, поток выполнения, синхронизация и публичный контракт регистрации callback. Поэтому адаптер для камеры не реализован. Хост-меню остаётся пригодным для моделирования после подтверждения этих контрактов.
